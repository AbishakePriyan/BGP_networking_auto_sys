# Architecture and outstanding work

React/Vite uses a localhost FastAPI API and reconnecting WebSocket for state. The backend reads the protected FRR router's accepted IPv4 BGP table via fixed `docker exec ... vtysh` argument lists, compares origins to `authorized_prefixes.json`, records events in SQLite, and can apply a fixed peer/prefix filter. The controller checks that the filtered path disappears from the accepted table; a ping is a separate action. Actions and polling are serialized. The API is bound to loopback, with local frontend origins allowed. This is a prototype, not a hardened multiuser service.

The three FRR containers have distinct `bgpguard-v2-*` names on the internal `bgpguard-v2_lab` bridge. R1 AS65001 announces `10.199.113.0/24`, R2 AS65002 is protected, R3 AS65003 can announce `10.199.113.0/25` to R2 and blackholes that route. The test destination is `10.199.113.10` on R1. These private v2 addresses keep both the routers and destination within the internal bridge's 10.199.0.0/16 network, so Docker Desktop's internal filtering permits the demonstration traffic; the more-specific BGP route still wins over the connected /16. The original lab is separate.

RIPE MRT updates can be cached, checksummed and filtered through BGPKIT. Exported observations use unknown labels until there is reviewed evidence. Replay reads that file, uses observation timestamp differences for playback, and cannot issue live actions. The current sample is not a verified incident, and playback speed is not a measurement of detection latency. Data ingestion needs robust incident evidence, RIB baseline construction, conservative matching and exclusion rules before supervised training. Model compatibility checks, causal feature history, incident-level splitting, reproducible evaluation, full run and alert lifecycle, reliable stale/failed state reconciliation, and comprehensive tests are future work.
